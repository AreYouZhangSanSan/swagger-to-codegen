## 2. 技术领域

本发明涉及计算机程序自动生成技术领域，具体涉及一种对接口契约文档进行确定性解析，基于多源证据识别接口业务角色并构建可审计中间表示，依据所述中间表示生成接口调用代码、类型代码和页面代码，对页面代码执行分级质量校验，并基于生成基线摘要、当前文件摘要和候选文件摘要识别人工修改、控制增量写入的方法。

## 3. 背景技术

前后端分离系统通常由后端通过接口契约文档描述路径、请求参数、请求体和响应数据结构，前端再据此编写接口调用、类型定义、列表页面、详情页面和表单页面。现有实现大致分为两类。

第一类为模板式代码生成器。该类工具根据 HTTP 路径和 Schema 生成固定结构代码，生成结果稳定，但依赖规范化的接口命名和固定工程模板。面对不一致的 `operationId`、自定义响应包装、嵌套类型以及不同 UI 组件体系时，往往需要大量人工修正。

第二类为生成模型式代码生成器。该类工具把接口文档、参考页面或自然语言指令发送给生成模型，由模型直接输出页面代码，具有较强适配能力，但存在字段幻觉、接口误用、输出不可追溯、静态错误和非确定性等问题。

在持续开发过程中，接口契约还会多次变化。传统生成器通常直接覆盖目标文件，无法区分文件中哪些内容仍是机器生成、哪些内容已经由程序员修改。开发人员为了避免劳动成果丢失，只能停止重新生成，或者把生成文件复制到其他位置后手工比较，使代码生成工具退化为一次性工具。

## 4. 现有技术存在的具体技术问题

### 4.1 契约信息在转换中丢失

路径参数可能被转换为静态字符串。例如接口路径 `/users/{id}` 被错误生成为 `/users/:id`，运行时未将参数值写入目标 URL。嵌套 `$ref` 类型可能只生成直接引用类型，造成依赖类型缺失和编译失败。

### 4.2 接口业务角色识别不可靠

不同后端可能分别使用 `page`、`list`、`query` 表示列表查询，使用 `save`、`create`、`add` 表示新增。仅依靠单个路径关键词容易把接口错误识别为列表、详情、创建、更新或删除操作，错误又会继续传播到按钮、表单和页面交互代码。

### 4.3 确定性事实与模型推断混合

接口路径、参数和 Schema 属于契约确定事实，页面布局和交互方式属于可推断信息。若二者不加区分地发送给生成模型，模型可能修改函数名、虚构字段或引用不存在的接口，难以解释错误来源。

### 4.4 错误代码可能先污染工程

部分生成流程先把模型输出写入正式文件，再执行格式化或类型检查。即使检查失败，原有可运行文件也已经被破坏。修复过程若继续覆盖正式文件，还会扩大错误影响范围。

### 4.5 再次生成会覆盖人工修改

现有生成器通常只比较“当前内容”和“新内容”，无法判断当前内容的差异来自接口契约变化还是人工修改，因此无法在自动更新和保护人工代码之间作出可靠选择。

### 4.6 模型输出存在文件系统风险

模型可能返回绝对路径或包含父目录跳转的路径。若生成器直接写入，可能修改输出目录之外的工程文件。

## 5. 发明目的

本发明旨在提供一种可审计、可校验、可持续增量更新的前端代码生成方法，在异构接口契约和不同前端工程风格条件下：

1. 保持接口路径、参数和类型依赖的完整性；
2. 降低接口角色误识别和模型字段幻觉；
3. 阻止未通过质量校验的候选代码污染正式工程；
4. 自动识别人工修改，并在默认情况下避免覆盖；
5. 对每次生成、冲突、备份和修复形成可追溯记录；
6. 提高生成代码的接口映射正确率和首次静态检查通过率。

## 6. 技术方案概述

本发明的核心不是简单地把“OpenAPI 生成代码”“大模型生成页面”和“文件备份”并列组合，而是形成以下相互作用的闭环：

```text
接口契约输入
  → 契约校验与确定性事实提取
  → 多源证据融合及角色置信度计算
  → 可审计中间表示和生成边界
  → 确定性 API/类型生成 + 受约束页面生成
  → 输出路径校验
  → 格式化、静态检查及限定范围修复
  → 合格候选代码
  → 三摘要增量判定
  → 创建 / 安全更新 / 保持不变 / 隔离冲突 / 备份后覆盖
  → 清单和运行报告
```

其中：

- 契约证据和置信度确定哪些接口、字段可以进入生成阶段；
- 质量门禁确定候选代码是否可以进入正式写入阶段；
- 三摘要增量判定确定合格候选代码如何与当前工程合并；
- 清单和报告把上述决策连接为可审计闭环。

## 7. 术语和数据对象

### 7.1 接口契约文档

用于描述接口路径、HTTP 方法、参数、请求体、响应体和数据类型的机器可读文档，包括但不限于 OpenAPI 或 Swagger 文档。

### 7.2 契约事实

从接口契约直接读取或经确定性转换得到的信息，例如 HTTP 方法、原始路径、路径参数、查询参数、请求 Schema、响应 Schema 和类型引用关系。

### 7.3 推断证据

用于判断接口业务操作角色的信息，包括 HTTP 方法证据、路径结构证据、语义关键词证据、Schema 结构证据以及模块内接口互补证据。

### 7.4 可审计中间表示

记录契约事实、推断结果、推断证据、置信度、复核标记和生成约束的数据结构，以下简称 IR。

示例：

```json
{
  "method": "GET",
  "path": "/api/users/{id}",
  "operationId": "getUserDetail",
  "inferredRole": "detail",
  "confidence": 0.8,
  "evidence": [
    "HTTP GET",
    "命中关键词 detail",
    "路径包含资源标识"
  ],
  "requiresReview": false
}
```

### 7.5 生成基线摘要

某一文件上次由生成器成功写入后计算并保存的内容摘要，记为 `H_base`。

### 7.6 当前文件摘要

再次生成时对目标文件当前内容计算的摘要，记为 `H_current`。

### 7.7 候选文件摘要

对本次通过质量校验的候选代码计算的摘要，记为 `H_candidate`。

## 8. 详细技术方案

### 8.1 步骤 S101：获取并校验接口契约

接收网络地址或本地文件路径，读取 JSON 或 YAML 格式接口契约，并至少执行以下校验：

1. 文档对象非空；
2. 包含版本标识；
3. 包含路径集合；
4. 网络读取设置超时时间；
5. 解析失败时停止生成，避免使用部分或错误契约。

### 8.2 步骤 S102：提取契约事实并构建类型引用图

按模块标签对接口操作进行分组。对每个操作提取：

- HTTP 方法；
- 原始接口路径；
- `operationId` 和摘要描述；
- 路径参数、查询参数和请求体；
- 成功响应 Schema；
- 直接引用类型。

以 Schema 为节点、`$ref` 引用关系为有向边构建类型引用图。从接口直接使用的类型集合出发，递归遍历对象属性、数组元素和类型引用，计算可达闭包：

```text
T0 = 接口直接引用类型集合
T(n+1) = T(n) ∪ references(T(n))
```

当 `T(n+1) = T(n)` 时停止，只生成闭包内类型。该方法既防止嵌套类型遗漏，也避免输出与目标模块无关的大量类型。

### 8.3 步骤 S103：基于多源证据识别业务角色

预设业务角色集合：

```text
R = {list, detail, create, update, delete, custom}
```

针对每个接口操作，从以下来源获得证据：

1. HTTP 方法，例如 GET 对列表或详情形成支持证据；
2. `operationId`、摘要和路径中的语义关键词；
3. 路径是否包含资源标识；
4. 是否存在请求体以及请求体字段特征；
5. 响应为集合、分页对象或单一对象；
6. 同模块是否存在互补操作。

对于角色 `r`，置信度可按下式计算：

```text
C(r) = min(1, Σ wi × ei)
```

其中，`ei` 表示第 i 项证据是否成立或其归一化强度，`wi` 表示对应权重。选择最高置信度角色：

```text
r* = argmax C(r)
```

当 `C(r*) < θ` 时，将接口标记为需要人工复核。阈值 `θ` 可配置，例如 0.55。对于删除、修改等高风险角色，可配置更高阈值。

当前实施代码已经实现 HTTP 方法、语义关键词和路径资源标识证据；Schema 结构证据和模块互补证据可作为进一步实施方式。

### 8.4 步骤 S104：构建可审计 IR

IR 至少包括：

```text
模块信息
接口契约事实
类型依赖闭包
候选业务角色
置信度
判断证据
人工复核标记
允许生成的字段和函数
禁止模型修改的约束
```

契约事实和推断信息分别存储，生成模型仅能在 IR 确定的接口、函数和字段范围内生成页面，不允许自行增加业务字段或改变 API 名称。

### 8.5 步骤 S105：分层生成代码

#### 8.5.1 确定性生成层

通过规则程序生成：

- API 函数；
- 路径参数模板插值；
- 查询参数与请求体；
- Promise 返回类型；
- 类型导入；
- 类型依赖闭包。

例如把：

```text
/api/users/{id}
```

确定性转换为：

```typescript
`/api/users/${id}`
```

#### 8.5.2 受约束生成层

将 IR、风格规范和参考页面组织为模型输入。模型只负责页面布局、控件组合和交互适配。输入中明确区分：

- 强约束：API 函数名、导入路径、业务字段、请求参数；
- 弱约束：页面布局、组件选型、视觉风格；
- 禁止项：参考模板中的旧业务字段、IR 中不存在的接口和字段。

模型配置至少记录模型标识和温度参数，以便生成结果复现和审计。

### 8.6 步骤 S106：输出路径边界校验

对模型返回的每个文件路径：

1. 将分隔符规范化；
2. 拒绝绝对路径；
3. 拒绝包含父目录跳转的路径；
4. 解析目标绝对路径；
5. 验证目标路径位于预设输出根目录内；
6. 禁止业务文件写入生成器元数据目录。

任一条件不满足时终止该文件写入。

### 8.7 步骤 S107：分级质量门禁和局部修复

候选页面代码在写入正式文件前依次执行：

```text
代码格式化
→ 语法检查
→ 类型检查
→ 可选工程构建检查
```

检查使用临时文件，不预先覆盖目标文件。当检查失败时，向生成模型提供：

- 当前失败文件代码；
- 结构化静态错误；
- 与该文件对应的 IR 节点；
- 允许修改范围；
- 最大修复次数。

模型返回修复候选后重新进入质量门禁。超过重试上限仍失败时，记录质量失败结果，不覆盖正式目标文件。

### 8.8 步骤 S108：基于三摘要的增量写入判定

候选代码通过质量门禁后，计算 `H_candidate`，读取 `H_base`，并在目标文件存在时计算 `H_current`。

判定规则如下：

| 条件 | 状态 | 处理方式 |
|---|---|---|
| 目标文件不存在 | created | 原子写入候选代码，更新基线 |
| `H_current = H_candidate` | unchanged | 不重复写入，更新或确认基线 |
| `H_base` 存在且 `H_current = H_base` | updated | 判定无人工作修改，原子写入候选代码，更新基线 |
| `H_current ≠ H_base` 或不存在可信基线 | conflict | 保留当前文件，候选代码写入隔离冲突目录，不更新该文件基线 |
| 存在显式强制指令 | forced | 先备份当前文件，再写入候选代码并更新基线 |

该判定的关键在于引入 `H_base`。仅比较当前内容与候选内容只能知道两者不同，无法判断差异是否包含人工修改；增加生成基线后，可以确定当前文件是否仍保持上次机器生成状态。

### 8.9 步骤 S109：原子写入、冲突隔离和备份

安全更新时，先在目标文件同级或目标存储系统的临时区域写入完整候选内容，完成后通过原子替换操作更新目标文件，降低进程中断导致半写入文件的概率。

冲突文件按照运行标识和相对路径隔离保存：

```text
.codegen/conflicts/<run-id>/<relative-path>.generated
```

强制覆盖前的人工版本保存为：

```text
.codegen/backups/<run-id>/<relative-path>
```

### 8.10 步骤 S110：生成清单和运行报告

生成清单至少保存：

```json
{
  "path": "modules/user.ts",
  "generatedHash": "...",
  "generator": "openapi-api",
  "contractSource": "openapi.json",
  "updatedAt": "..."
}
```

每次运行报告至少保存：

- 运行标识；
- 开始和结束时间；
- 输出根目录；
- 是否使用强制模式；
- 每个文件的当前摘要和候选摘要；
- `created`、`unchanged`、`updated`、`conflict` 或 `forced` 状态；
- 冲突候选路径或备份路径；
- 汇总计数。

## 10. 关键技术特征之间的相互作用

为避免被认为是常规功能拼接，申请文件应重点描述以下相互作用：

1. IR 中的置信度和复核标记控制接口是否进入页面生成，减少错误接口向后传播；
2. IR 中的契约事实构成模型强约束，使静态错误能够映射回具体接口和字段；
3. 质量门禁只把通过检查的代码交给三摘要判定，避免把错误代码记录为新基线；
4. 三摘要判定利用上次成功写入形成的基线识别人工修改；
5. 冲突状态不更新基线，确保下一次生成仍能识别目标文件与可信机器版本的偏离；
6. 强制覆盖先备份、后更新基线，使覆盖操作可恢复且可审计；
7. 运行报告同时记录契约来源、生成方式、质量结果和写入结果，形成端到端追溯链。

## 11. 有益技术效果

与固定模板生成或直接模型生成相比，本发明至少具有以下效果：

1. 通过类型引用闭包降低嵌套类型遗漏，同时减少无关类型传输和输出；
2. 通过多源证据和置信度减少接口角色误识别；
3. 通过事实/推断分离降低模型虚构接口和字段的概率；
4. 通过写入前质量门禁避免错误代码污染正式工程；
5. 通过三摘要判定自动识别人工修改，避免二次生成造成代码丢失；
6. 通过冲突隔离和强制备份提供可恢复的增量更新；
7. 通过路径边界校验阻止生成文件越出目标目录；
8. 通过生成清单和运行报告提高生成过程可追溯性。

上述效果应通过申请日前完成的实验数据进行支持，不应只保留定性表述。

## 12. 具体实施例

### 12.1 实施例一：用户模块首次生成

输入接口契约包含：

```text
GET  /api/users
GET  /api/users/{id}
POST /api/users
PUT  /api/users/{id}
DELETE /api/users/{id}
```

系统按 Tag 得到用户模块。对于 `GET /api/users/{id}`，获得 GET 方法证据、路径资源标识证据和 detail 语义证据，将其角色识别为详情接口。生成器把路径转换成 `` `/api/users/${id}` ``，生成 `Promise<User>` 返回类型。

若 `User` 的 `profile` 属性引用 `Profile`，而 `Profile` 又引用 `Address`，系统计算类型闭包 `{User, Profile, Address}`，只生成上述可达类型。

页面候选通过路径校验、格式化和类型检查后，由增量写入模块发现目标文件不存在，状态记为 `created`，写入目标文件并保存生成基线摘要。

### 12.2 实施例二：接口变化但没有人工修改

后端为 `User` 新增 `phone` 字段。再次生成时：

```text
H_current = H_base
H_candidate ≠ H_current
```

系统判定当前文件仍是上次机器生成版本，状态为 `updated`，安全写入包含 `phone` 的候选代码，并更新生成基线。

### 12.3 实施例三：存在人工修改

程序员在生成的页面中增加权限校验。此时：

```text
H_current ≠ H_base
H_candidate ≠ H_current
```

系统判定存在人工修改，保持目标页面不变，把候选页面写入冲突目录，状态记为 `conflict`，并且不更新该文件的基线摘要。程序员可使用 IDE 比较当前文件和候选文件后人工合并。

### 12.4 实施例四：强制更新

用户确认需要接受新候选代码并发出强制更新指令。系统先把当前人工版本写入备份目录，再原子替换目标文件，状态记为 `forced`，最后把候选摘要记录为新基线。

### 12.5 实施例五：候选代码类型检查失败

模型生成页面引用不存在的组件。系统把候选内容写入临时检查文件，静态检查返回错误。系统将失败文件、错误信息和对应 IR 节点发送给模型进行限定范围修复。达到最大重试次数仍失败时，记录质量失败，不进入三摘要写入阶段，因此现有目标文件和生成基线均不改变。

## 13. 可替代实施方式

1. 内容摘要算法可使用 SHA-256、SHA-3 或其他抗碰撞摘要算法；
2. 生成清单可以保存于本地 JSON、数据库、对象存储或版本控制元数据中；
3. 冲突隔离可以保存完整候选文件，也可以保存差异块；
4. 静态检查可以是 TypeScript 类型检查、编译检查、Lint、单元测试或其组合；
5. 生成模型可以是远程大语言模型、本地模型或规则模型；
6. 角色证据权重可以由人工配置、统计学习或历史生成反馈调整；
7. 页面可以是 Vue、React、Angular、小程序或其他客户端代码；
8. 契约可以是 OpenAPI、GraphQL Schema、RPC 描述文件或自定义接口元数据；
9. 人工代码保护还可以扩展到语法树节点级或标记区域级合并，但不影响文件级三摘要判定作为安全前置门禁。

## 15. 权利要求书草案框架

> 以下内容用于帮助代理师识别必要技术特征，不建议未经检索和法律审校直接提交。

### 15.1 独立权利要求1：方法

一种前端代码生成方法，其特征在于，包括：

1. 获取接口契约文档，从所述接口契约文档提取多个接口操作的契约事实以及类型引用关系；
2. 针对各接口操作，根据至少包括请求方法、接口路径结构和接口语义信息的多项证据，确定所述接口操作对应的业务操作角色、角色置信度和复核标记，并基于所述契约事实、类型引用关系、业务操作角色、角色置信度和复核标记构建可审计中间表示；
3. 根据所述可审计中间表示生成接口调用代码和类型代码，并将所述可审计中间表示限定的接口和字段作为约束输入生成模型，以获得页面候选代码；
4. 在不覆盖目标文件的情况下对所述页面候选代码执行静态质量校验，并在校验失败时根据静态错误信息和对应的可审计中间表示对限定代码范围进行修复；
5. 在候选代码通过静态质量校验后，获得目标文件上次成功生成时的生成基线摘要、目标文件当前内容的当前文件摘要以及所述候选代码的候选文件摘要；
6. 根据所述生成基线摘要、当前文件摘要和候选文件摘要之间的比较结果，从保持不变、安全更新、隔离冲突和备份后覆盖中选择目标文件处理方式，并记录处理结果。

### 15.2 从属权利要求候选

2. 根据权利要求1所述的方法，其中，通过递归遍历类型引用、对象属性和数组元素计算从接口直接引用类型出发的可达类型闭包，并仅生成所述可达类型闭包内的类型代码。

3. 根据权利要求1所述的方法，其中，当最高角色置信度低于预设阈值时设置所述复核标记，并禁止对应接口进入预设高风险页面操作的自动生成。

4. 根据权利要求1所述的方法，其中，接口调用代码由确定性程序生成，页面候选代码由生成模型生成，且生成模型的输入包含禁止修改的接口函数名、导入路径和业务字段。

5. 根据权利要求1所述的方法，其中，对页面候选代码依次执行路径边界校验、格式化、语法检查和类型检查。

6. 根据权利要求1所述的方法，其中，路径边界校验包括拒绝绝对路径、拒绝父目录跳转并验证规范化目标路径位于预设输出根目录内。

7. 根据权利要求1所述的方法，其中，当当前文件摘要等于候选文件摘要时保持目标文件不变。

8. 根据权利要求1所述的方法，其中，当当前文件摘要等于生成基线摘要且不同于候选文件摘要时，将候选代码原子写入目标文件并将候选文件摘要更新为新的生成基线摘要。

9. 根据权利要求1所述的方法，其中，当当前文件摘要不同于生成基线摘要时，保持目标文件不变，将候选代码写入与运行标识关联的冲突隔离位置，并保持原生成基线摘要不变。

10. 根据权利要求1所述的方法，其中，响应于强制更新指令，先将目标文件当前内容写入与运行标识关联的备份位置，再用候选代码替换目标文件并更新生成基线摘要。

11. 根据权利要求1所述的方法，其中，运行报告记录契约来源、生成器类型、当前文件摘要、候选文件摘要、处理状态以及冲突位置或备份位置。

## 16. 摘要草案

本发明公开一种基于接口契约证据约束和生成基线冲突判定的前端代码生成方法、装置、设备及存储介质。该方法从接口契约文档提取接口操作和类型引用关系，基于请求方法、路径结构及接口语义信息确定业务操作角色、置信度和复核标记，构建区分契约事实与推断信息的可审计中间表示；根据所述中间表示确定性生成接口调用代码和类型代码，并约束生成模型生成页面候选代码；在不覆盖目标文件的情况下执行静态质量校验；候选代码通过校验后，比较上次成功生成的基线摘要、目标文件当前摘要和候选摘要，根据比较结果执行保持不变、安全更新、冲突隔离或备份后覆盖，并记录运行报告。本发明能够减少接口和类型映射错误，阻止不合格候选代码污染工程，并在接口契约持续变化时识别和保护人工修改。

### 17.3 指标定义

| 指标 | 计算方式 |
|---|---|
| 接口映射正确率 | 正确映射的页面操作数 / 页面操作总数 |
| 路径参数正确率 | 正确插值的路径参数数 / 路径参数总数 |
| 类型闭包完整率 | 已生成的必要引用类型数 / 必要引用类型总数 |
| 字段幻觉率 | 契约中不存在的业务字段数 / 生成业务字段总数 |
| 首次静态检查通过率 | 首次通过模块数 / 总模块数 |
| 平均修复次数 | 修复调用总次数 / 发生修复的文件数 |
| 人工修改保护率 | 未被错误覆盖的人工修改文件数 / 人工修改文件总数 |
| 冲突识别准确率 | 正确识别的人工修改冲突数 / 实际冲突数 |
| 无关类型削减率 | 1 - 实际生成类型数 / 契约全部类型数 |
| 平均输入 token 数 | 各模块模型输入 token 总和 / 模块数 |
| 越界写入拦截率 | 被阻止的越界路径数 / 构造的越界路径总数 |

## 21. 撰写策略说明

根据2026年1月1日起施行的《专利审查指南》相关修改，涉及人工智能模型或算法具体应用的说明书，需要清楚说明模型或算法如何与具体场景结合，以及输入、输出数据如何设置，使本领域技术人员能够实现。本交底书因此明确记载了模型输入中的 IR、约束项、静态错误和输出页面代码之间的关系。

本方案不把“使用大模型”本身作为发明点，而把重点放在：

```text
契约事实和证据的机器处理
→ 对生成边界的控制
→ 静态质量反馈
→ 三摘要增量写入决策
→ 计算机工程文件安全更新效果
```

正式申请时，应把技术问题表述为代码生成过程中接口信息错误传播、静态错误污染工程以及人工修改无法识别导致的工程文件损坏，而不是“减少人工工作量”这类偏业务效果。
